# Code Signing, Notarization & Entitlements

See also [`docs/PACKAGING.md`](PACKAGING.md) for the overall build pipeline this fits into.

## The unsigned path always works

Nothing in this repository requires a real Apple Developer certificate to build, test, or produce a DMG:

- `scripts/build-app.sh` always builds with `CODE_SIGNING_ALLOWED=NO`, `CODE_SIGN_IDENTITY="-"` — no identity, no certificate, ever.
- `scripts/package-release.sh` signs and notarizes **only if** the environment variables below are present, and otherwise produces `ClaudeSwap-<version>-unsigned.dmg` plus a clear log banner saying so.
- `.github/workflows/ci.yml` never reads any secret and always exercises the unsigned path.
- No script in this repository invents, generates, or fakes a certificate, identity, or signature. If you don't have real Apple Developer credentials yet, you get an honest unsigned build — never a build that pretends to be signed.

Unsigned + un-notarized apps trigger Gatekeeper's standard "Apple could not verify..." dialog; users can still open them via right-click → Open, or `xattr -d com.apple.quarantine ClaudeSwap.app`. That's expected for local/dev builds and is documented here so it isn't mistaken for a bug.

## What's required to produce a signed, notarized release

You need an active **Apple Developer Program** membership and a **Developer ID Application** certificate (Developer ID, not App Store — see "Not the Mac App Store" below).

| Secret (GitHub Actions) | What it is | Used by |
|---|---|---|
| `CODESIGN_IDENTITY` | Exact signing identity string, e.g. `Developer ID Application: Jane Doe (ABCDE12345)` | `scripts/package-release.sh` (`codesign --sign`) |
| `CODESIGN_CERT_P12_BASE64` | `base64` of your Developer ID Application certificate exported as `.p12` | `release.yml` (imports into a throwaway CI keychain) |
| `CODESIGN_CERT_PASSWORD` | Password you set when exporting the `.p12` | `release.yml` |
| `APPLE_TEAM_ID` | Your 10-character Apple Developer Team ID | `scripts/package-release.sh` (notarization) |
| `APPLE_ID` | Apple ID email used to submit for notarization | `scripts/package-release.sh` (`notarytool`) |
| `APPLE_APP_SPECIFIC_PASSWORD` | An [app-specific password](https://support.apple.com/102654) for that Apple ID (not your main password) | `scripts/package-release.sh` (`notarytool`) |
| `SPARKLE_PRIVATE_KEY` | base64 ed25519 private key generated by Sparkle's `generate_keys` tool | `scripts/package-release.sh` (signs the appcast enclosure) |

Generating each of these:

```sh
# 1. Create/download a "Developer ID Application" certificate from
#    https://developer.apple.com/account/resources/certificates/list
#    (or Xcode → Settings → Accounts → Manage Certificates → +).

# 2. Export it (with its private key) as a .p12 from Keychain Access, then:
base64 -i DeveloperIDApplication.p12 | pbcopy   # -> CODESIGN_CERT_P12_BASE64

# 3. Generate an app-specific password at https://appleid.apple.com
#    (Sign-In and Security -> App-Specific Passwords) -> APPLE_APP_SPECIFIC_PASSWORD

# 4. Sparkle keys (from a checkout of sparkle-project/Sparkle's release tools, or
#    the `generate_keys` binary from their Sparkle-distribution-*.tar.xz release asset):
./bin/generate_keys
# prints/stores the private key in your login Keychain and prints the public key
# to embed in Info.plist as SUPublicEDKey. Export the private key for CI with
# ./bin/generate_keys -x /tmp/sparkle_private_key && base64 -i /tmp/sparkle_private_key
```

Store all of the above as **repository or environment secrets** in GitHub (Settings → Secrets and variables → Actions). Never commit any of them; `.github/workflows/*.yml` only ever reference them via `${{ secrets.* }}`.

Rotate `CODESIGN_CERT_PASSWORD`/`APPLE_APP_SPECIFIC_PASSWORD` if you ever suspect they leaked, and revoke+reissue the certificate itself from the Apple Developer portal if the `.p12` leaked.

## Entitlements: no App Sandbox

`ClaudeSwap.app` does **not** enable `com.apple.security.app-sandbox`. See [`docs/PACKAGING.md`](PACKAGING.md#not-distributed-via-the-mac-app-store-no-app-sandbox) for the reasoning (Keychain access matching the existing CLI tool's usage, and unrestricted `~/.claude` access). Concretely, the entitlements file (lives under `ClaudeSwap/**`/the Xcode project) should:

- **Omit** `com.apple.security.app-sandbox` entirely (its absence is what makes this a non-sandboxed, Developer-ID-only app — it cannot be submitted to the Mac App Store like this).
- **Enable the Hardened Runtime** (`com.apple.security.cs.*` family applies here) — required for notarization regardless of sandboxing. Hardened Runtime and App Sandbox are independent switches; we want the former without the latter.
- Consider `com.apple.security.cs.disable-library-validation` if the embedded PyInstaller helper's process loads any native extension module (`.so`) that isn't signed with the *same* Team ID as `ClaudeSwap.app` (this is common with wheels built by third parties, e.g. some cryptography/keyring backends). The alternative — re-signing every vendored `.so` yourself with your own identity — is more correct but more brittle across core version bumps; `scripts/package-release.sh` already re-signs each embedded binary it finds when `CODESIGN_IDENTITY` is set, which covers the common case, but library-validation issues with deeply-nested native deps may still require this entitlement in practice. Verify with `codesign --verify --deep --strict` (which `package-release.sh` already runs) and Console.app's crash/refusal logs before deciding you need it.
- Keychain access itself does not require a sandbox entitlement when unsandboxed — a non-sandboxed, hardened-runtime app talks to the Keychain the same way a command-line tool does (subject to the normal per-item ACL prompts).

None of the entitlements file lives in `scripts/**`/`Dependencies/**`/`.github/workflows/**`, so it's out of scope for this role to author — this section exists so whoever owns it has the constraint spelled out and doesn't accidentally add `app-sandbox` later.

## How `package-release.sh` signs and notarizes

Roughly, when `CODESIGN_IDENTITY` is set:

1. Every executable/dylib/`.so` under the helper's relocated support tree at `Contents/Frameworks/` (see [`docs/PACKAGING.md`](PACKAGING.md#how-the-helper-is-actually-embedded-and-why-its-not-just-a-file-copy) for why it lives there and not next to the executable) is signed individually first (`codesign --force --timestamp --options runtime --sign "$CODESIGN_IDENTITY"`), then the helper executable itself at `Contents/MacOS/claude-swap-helper`.
2. The outer `.app` is signed (`codesign --force --deep --timestamp --options runtime`).
3. `codesign --verify --deep --strict --verbose=2` is run as a sanity check before packaging continues.
4. The DMG is built from the now-signed `.app`.
5. If `APPLE_ID` / `APPLE_APP_SPECIFIC_PASSWORD` / `APPLE_TEAM_ID` are *also* set, the DMG is submitted via `xcrun notarytool submit --wait` and the resulting ticket is stapled with `xcrun stapler staple`.

If only signing (not notarization) credentials are present, you get a signed-but-not-notarized DMG plus a warning — still useful for local testing on your own Mac, but Gatekeeper will refuse it on other people's Macs until notarized.

## CI keychain handling (`release.yml`)

GitHub-hosted macOS runners need a keychain to import the `.p12` into before `codesign` can use it. `release.yml`'s "Import signing certificate" step:

1. Creates a throwaway keychain (`security create-keychain`) with a randomly generated password that never leaves the job.
2. Imports the certificate (`security import ... -T /usr/bin/codesign`).
3. Adds it to the runner's keychain search list and sets a partition list so `codesign` can use it non-interactively (`security set-key-partition-list`).
4. Deletes the decoded `.p12` file immediately after import.

The runner (and its keychain) is destroyed at the end of the job either way, so no persistent cleanup step is required — but never reuse a persistent/self-hosted runner for this without adding one.

## Required-but-optional, one more time

Every credential in this document is **optional** from the pipeline's point of view: `ci.yml` never needs any of them, and `release.yml`/`package-release.sh` degrade to an unsigned/un-notarized build if some or all are missing. Treat "required" here as "required to ship a notarized release to end users outside your own Mac", not "required for this repo's CI or local dev to function".
